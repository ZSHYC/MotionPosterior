# TrackNetV5 轨迹导出与推理兼容性改造说明

> 本文记录历史 TrackNetV5 兼容链路的行为与约束。项目公开名称现为
> **MotionPosterior**；文中保留 TrackNetV5 名称是为了准确描述旧接口、旧权重和
> 既有 CSV 契约。新的运动模型入口请参考 `MotionPosteriorNet` 与
> `motion_posterior3/5` 配置。

## 1. 文档目的

本文说明本次 TrackNetV5-SDK 推理链路改造的背景、问题、设计依据、具体修改、
兼容性影响和验证结果，供后续向上游仓库提交 Pull Request 时审阅。

本次改造只处理推理阶段的轨迹导出和公开备用推理接口，不修改 TrackNetV5 的模型
架构、训练代码或权重参数，也没有使用真实权重运行视频。

对应实现提交：

```text
53c09619559c7d08ee22326d5f0042224f5bc699
```

## 2. 改造目标

改造前的批量推理脚本更偏向人工查看结果，输出内容不适合作为下游训练数据。
本次改造希望形成一个稳定、可验证的逐帧轨迹契约：

1. 每个实际解码帧恰好对应一条轨迹记录。
2. 帧号统一从 0 开始。
3. 同时保存模型空间坐标和原视频分辨率坐标。
4. 保存视频 FPS、宽度和高度，避免下游猜测元数据。
5. CSV 只包含结构化轨迹，不混入统计文本。
6. 默认只生成轨迹 CSV，不强制生成体积较大的可视化视频。
7. 输入或模型输出不合法时立即失败，避免产生不完整但看似正常的结果。
8. `track.py`、`infer.py` 和公开的 `core` 接口遵循一致的关键行为。

## 3. 模型输入输出分析

### 3.1 外部输入是 9 通道三帧图像

推理脚本一次读取连续三帧，每帧是 RGB 三通道，经过
[`ConcatChannels`](../datasets_factory/transforms/tracknet_transforms.py) 后得到：

```text
[B, 9, 288, 512]
```

其中 9 个通道的排列为：

```text
前一帧 RGB + 当前帧 RGB + 后一帧 RGB
```

### 3.2 TrackNetV5 内部主干实际接收 13 通道

[`TrackNetV5`](../models_factory/models/tracknetv5.py) 先通过 MDD 计算四个运动注意力
通道，再按以下顺序拼接：

```text
F1(3) + attention_12(2) + F2(3) + attention_23(2) + F3(3)
```

因此主干网络接收：

```text
3 + 2 + 3 + 2 + 3 = 13 通道
```

这也是 V5 配置中 `TrackNetV2Backbone(in_channels=13)` 的原因。不能因为外部输入为
9 通道，就把 V5 主干的 `in_channels` 改成 9。

### 3.3 输出是三张 512×288 热力图

R-STR Head 对三帧分别输出一张概率热力图：

```text
[B, 3, 288, 512]
```

三张热力图依次对应输入的三帧。

坐标后处理不是直接取全局最大值，而是：

1. 将概率热力图转换为 `uint8`。
2. 按阈值进行二值化。
3. 选择面积最大的连通轮廓。
4. 使用轮廓矩计算几何质心。
5. 使用该轮廓内部的最大热力图值作为置信度。

### 3.4 为什么没有修改模型输入分辨率

[`R_STRHead`](../models_factory/heads/r_strhead.py) 默认使用：

```text
img_size = (288, 512)
patch_size = 16
```

空间位置编码的 patch 数量在初始化时固定为：

```text
(288 / 16) × (512 / 16) = 18 × 32 = 576
```

模型还包含三帧时间位置编码。直接把输入改成原视频尺寸会改变 patch 数量，使空间位置
编码形状和已有权重不匹配。因此本次保留 `512×288` 模型空间，通过显式坐标换算恢复
原视频坐标，而不是修改模型结构。

### 3.5 为什么要求输入视频为 16:9

当前预处理使用 `cv2.resize` 直接缩放到 `512×288`，没有 letterbox 或裁剪逻辑。
如果输入不是 16:9，画面会发生非等比形变。即使输出坐标再分别乘以宽高比例，也只能
恢复数值范围，不能消除模型推理时已经发生的图像形变。

因此当前实现明确拒绝非 16:9 视频，避免静默生成几何意义不可靠的轨迹。将来如果需要
支持其他宽高比，应单独设计 letterbox、有效区域映射和训练/推理一致性方案。

## 4. 改造前存在的问题

### 4.1 CSV 坐标仍处于模型空间

旧脚本输出的 `x/y` 是 `512×288` 热力图坐标，但文件中没有坐标系说明，也没有原视频
宽高。对于 1280×720、1920×1080 等视频，下游若直接使用这些坐标，会导致位置和距离
特征整体缩放错误。

### 4.2 CSV 尾部混入统计行

旧 CSV 在正常轨迹行之后追加：

```text
total_detected_frame,...
detection_ratio,...
```

这些行不符合逐帧 schema。标准 `csv.DictReader` 仍可能把它们读成普通数据行，导致
帧号解析失败或产生脏数据。

### 4.3 视频总帧数不是 3 的倍数时会丢尾帧

旧实现每次连续读取三帧，只要其中一帧读取失败就直接退出。因此：

- 总帧数为 `3n+1` 时丢失最后 1 帧；
- 总帧数为 `3n+2` 时丢失最后 2 帧。

这会破坏“视频帧与轨迹行一一对应”的基本契约。

### 4.4 过度依赖容器声明的帧数

视频容器的 `CAP_PROP_FRAME_COUNT` 不一定等于实际可解码帧数。旧 `core` 检测器先按
声明帧数创建结果列表，可能留下默认漏检项，或无法容纳额外解码出的帧。

### 4.5 默认生成多份可视化视频

旧脚本对每个输入视频默认生成轨迹视频和热力图对比视频。批量生成训练轨迹时，这会带来
额外的编码时间和磁盘占用，而训练管线实际只需要 CSV。

### 4.6 两个入口维护了两份不同实现

`track.py` 和 `infer.py` 原本各自保存一整套推理代码。两份实现的坐标、置信度和输出
格式并不完全一致，后续修改其中一个入口时很容易再次产生行为分叉。

### 4.7 CLI 在校验输入前加载模型

旧主流程先构建模型、读取权重，再检查输入目录和视频文件。路径错误或目录为空时仍会
消耗模型初始化时间，并且权重异常可能遮蔽真正的输入配置错误。

### 4.8 V4 被公开为可选项，但实际无法构建

CLI 和 `core` 配置都宣称支持 V4，但当前注册表没有注册 `TrackNetV4`，相关 Head 配置
与调用签名也不一致。保留该选项会让用户在运行时遇到确定性的构建失败。

### 4.9 阈值 1.0 是无效配置

OpenCV 的二值化条件是像素值严格大于阈值。当概率图转换成 `uint8` 后最大值是 255；
若阈值参数为 `1.0`，换算后的阈值同样是 255，因此没有任何像素能够通过。

### 4.10 `core` 可视化链路坐标和 FPS 不正确

旧 `core.detector` 返回模型空间坐标，但 `core.pipeline` 直接把它画到原分辨率视频，
会产生明显错位。

同时，渲染链路把 FPS 强制转换为整数。例如 29.97 FPS 会变成 29 FPS，导致输出视频
时长漂移。视频读取器和写入器是否成功打开也没有检查。

## 5. 新的标准 CSV 契约

每个输入视频生成一个同 stem CSV：

```text
video/20260706_001.mp4
    ↓
tracknetv5/20260706_001.csv
```

固定表头如下：

```text
benchmark_id,video_name,frame_number,detected,x_512,y_288,x_orig,y_orig,conf,fps,width,height
```

### 5.1 字段定义

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `benchmark_id` | string | 样本身份，当前取视频文件的 stem |
| `video_name` | string | 完整视频文件名，包含扩展名 |
| `frame_number` | int | 0-based 实际解码帧号 |
| `detected` | 0/1 | 该帧是否检测到球 |
| `x_512` | float/empty | `512×288` 模型空间横坐标 |
| `y_288` | float/empty | `512×288` 模型空间纵坐标 |
| `x_orig` | float/empty | 原视频分辨率横坐标 |
| `y_orig` | float/empty | 原视频分辨率纵坐标 |
| `conf` | float | 最大轮廓内部的热力图峰值，范围约为 `[0,1]` |
| `fps` | float | 视频容器报告的 FPS，保留小数 |
| `width` | int | 原视频宽度 |
| `height` | int | 原视频高度 |

### 5.2 坐标换算

对检测成功的帧：

```text
x_orig = x_512 × width / 512
y_orig = y_288 × height / 288
```

例如模型坐标为 `(269, 203)`，原视频为 `1280×720`：

```text
x_orig = 269 × 1280 / 512 = 672.5
y_orig = 203 × 720 / 288 = 507.5
```

### 5.3 未检测帧

未检测帧写为：

```text
detected = 0
x_512/y_288/x_orig/y_orig = 空单元格
conf = 0.0
```

不再使用 `(0,0)` 表示缺失，因为 `(0,0)` 本身是合法画面坐标。

### 5.4 完整性约束

CSV 以实际解码结果为准：

- 每个实际解码帧写一行；
- 帧号严格递增；
- 第一帧编号为 0；
- 不依赖可能不准确的容器帧数决定最终行数；
- 不在 CSV 尾部追加统计记录。

## 6. 尾帧处理策略

TrackNetV5 每次需要三帧输入。对于最后不足三帧的情况，当前策略为：

1. 保存本次实际读取到的帧数；
2. 重复最后一张实际帧，直到输入数量达到三张；
3. 正常执行一次模型推理；
4. 只导出实际存在帧对应的前 `N` 个输出；
5. 不为补齐帧创建 CSV 行。

例如视频最后只剩两帧：

```text
模型输入：frame_3, frame_4, frame_4
CSV 输出：只写 frame_3 和 frame_4
```

这样既不会丢帧，也不会把尚未推理的尾帧无条件标为漏检。

## 7. CLI 行为变化

### 7.1 新命令

```bash
python track.py <input_dir> <weights_path> \
  --arch v5 \
  --output-dir <trajectory_csv_dir> \
  --threshold 0.5 \
  --device cuda:0
```

可选生成可视化视频：

```bash
python track.py <input_dir> <weights_path> \
  --arch v5 \
  --output-dir <trajectory_csv_dir> \
  --visualization-dir <visualization_dir>
```

### 7.2 `--output-dir` 改为必填

旧实现将结果隐式写入输入目录内部。新实现要求显式指定轨迹目录，原因是：

- 不污染原始视频目录；
- 更容易接入不同数据集布局；
- 避免把模型架构名写死进路径；
- 调用方可以明确控制训练数据和可视化产物的位置。

### 7.3 可视化改为按需生成

未提供 `--visualization-dir` 时只生成 CSV。这样批量数据准备不会产生不需要的 MP4。

### 7.4 失败策略改为 fail-fast

以下情况现在会返回非零退出状态：

- 输入目录不存在；
- 权重文件不存在；
- 没有发现支持的视频；
- 同一目录中存在相同 stem、不同扩展名的视频；
- 阈值不是有限值或不在 `[0,1)`；
- 视频无法打开；
- FPS、宽度或高度无效；
- 视频不是 16:9；
- 模型输出形状不是 `[1,3,288,512]`。

旧实现会捕获单视频异常并继续运行，容易留下缺少部分文件的输出目录。新实现直接失败，
让批处理调度器能够发现问题并重新执行。

### 7.5 架构选项

CLI 当前公开：

```text
v2, v5
```

V4 代码文件仍保留在仓库中，但在注册和调用签名修复完成前，不再作为可运行选项公开。

主要修改：

- 增加固定模型尺寸常量和标准 CSV 字段；
- 增加单行 canonical 数据构造函数；
- 将模型坐标换算为原视频坐标；

- 修复最后 1–2 帧；

- 要求显式指定输出目录；
- 检查重复视频 stem；
- 先校验输入，再构建和加载模型；
- 改为 fail-fast；
- 移除不可用的 V4 CLI 选项。

### 8.2 `infer.py`

删除重复的旧推理实现，改为直接复用 `track.main`：

```python
from track import main
```

这是有意的删除性修改，用于确保两个历史入口永远使用同一份实现。

### 8.3 `core/detector.py`

同步修复 SDK 公开的备用检测接口：

- 移除不可用的 V4 配置；
- 校验阈值；
- 校验视频打开状态和 16:9 分辨率；
- 不再预分配容器声明帧数长度的结果；
- 按实际解码帧动态追加 `BallPoint`；
- 修复最后 1–2 帧；
- 校验模型输出形状；
- 将模型空间坐标换算回原视频坐标；
- 确保异常时释放 `VideoCapture`。

注意：这会改变 `TrackNetDetector.detect_video()` 返回坐标的语义。改造后 `BallPoint.x/y`
是原视频坐标，不再是 `512×288` 模型坐标。依赖旧坐标语义的调用方需要同步调整。

### 8.4 `core/pipeline.py`

主要修改：

- 保留浮点 FPS，不再使用 `int()` 截断；
- 校验输入视频是否成功打开；
- 校验 FPS、宽度和高度；
- 校验 `VideoWriter` 是否成功打开；
- 使用 `try/finally` 保证读取器、写入器和进度条被释放。

`core.detector` 已返回原视频坐标，因此渲染阶段可以直接在原视频画布上使用。

## 9. 兼容性和破坏性变化

### 9.1 有意保留的兼容性

- `infer.py` 文件仍然可以作为入口使用；
- V2 和 V5 的模型配置保留；
- 热力图转坐标的最大轮廓质心算法保持不变；
- 置信度仍来自最大轮廓内部的热力图峰值；
- 可视化能力仍然存在，只是改为显式启用。

### 9.2 有意发生的行为变化

| 旧行为 | 新行为 |
| --- | --- |
| 输出到 `input_dir/{arch}/...` | 由 `--output-dir` 显式指定 |
| 文件名为 `*_data.csv` | 文件名与视频 stem 相同 |
| CSV 只有模型空间 `x/y` | 同时输出模型空间和原视频空间坐标 |
| CSV 尾部追加统计文本 | 统计只输出到终端 |
| 默认生成两份视频 | 默认只生成 CSV |
| 尾部不足三帧直接丢弃 | 边界补帧推理，只输出实际帧 |
| 单视频失败后静默跳过 | 立即失败并返回非零状态 |
| CLI 宣称支持 V4 | 暂不公开不可运行的 V4 |
| `core` 返回模型空间坐标 | `core` 返回原视频坐标 |
| 渲染 FPS 强制取整 | 保留浮点 FPS |

这些变化会影响依赖旧目录、旧文件名或旧 `core` 坐标语义的调用方，因此 PR 描述中应
明确标记为推理输出契约升级。

## 12. 已知限制和后续建议

### 12.1 尾帧采用边界复制

不足三帧时复制最后一帧是确定、简单且不会丢行的策略，但它和真实的三帧连续运动上下文
仍有区别。如果未来需要对尾帧精度做专项优化，可以考虑重叠窗口，并通过真实标注比较
两种策略。

### 12.2 只支持 16:9

这是为了避免无提示的图像形变。若上游需要支持任意宽高比，建议新增统一的 letterbox
变换，并同时保存 padding、缩放比例和逆映射信息。

### 12.3 V2 只保留兼容入口

本次重点是 V5。V2 配置仍然公开，但本次没有使用 V2 权重执行端到端视频验证。

### 12.4 `track.py` 与 `core.detector` 仍有少量重复逻辑

两条公开入口都需要模型配置和热力图后处理。当前没有为此新增抽象层，是为了保持 PR
范围聚焦、减少额外重构。若未来两条入口继续共同演进，可在单独 PR 中提取共享模块。

### 12.5 真实权重验证待单独执行

本次验证刻意停在无权重结构、合成视频和 CSV 兼容性层面。合并前或发布前仍建议使用
一段短 16:9 视频执行真实权重 smoke test，重点检查：

- 权重能否严格加载；
- 输出热力图数值是否位于预期范围；
- CSV 行数是否等于实际解码帧数；
- 原图坐标是否落在画面边界内；
- 轨迹可视化位置是否与球一致；
- GPU 和 CPU 设备选择是否符合预期。
